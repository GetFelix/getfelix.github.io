Take a shard with five replicas and `Quorum` acknowledgement, and let it go quiet. Every record a client was promised sits on A, the leader, and on B and C. Then C loses its disk and comes back empty.

A kept reporting C as caught up. It did so on every pass, for as long as the shard stayed idle. If A then died, placement could promote C. C would fence with D and E, and its own empty log would count as a vote. The fence would complete without the records, and two faults on a five-copy shard would have lost data the client had been told was safe.

The fix was to stop trusting a follower's position and start asking which copy of the data it describes.

## What we found

A leader tracks each follower with a cursor. One field, `confirmed`, is the last position the follower answered holding. The report the leader sends to the control plane calls a follower caught up when `confirmed` reaches the position the leader reports against ([#1266](https://github.com/GetFelix/felix/issues/1266)).

Only shipping lowers `confirmed`. The leader sends a batch, the follower compares it against its own log and answers where it really is. On an idle shard there is nothing to send, so the exchange ends `UpToDate` without asking the follower anything. A follower that restarted at the same generation didn't touch the cursor either.

So the cursor was a photograph. It was taken the last time anyone asked, and nothing made the leader look again.

A leader's count of who holds a record is what lets it acknowledge under `Quorum`. It is also what a failover trusts when the leader is gone. Both were reading a number that nobody had checked since it was written.

## A name for the data

Each broker with durable storage keeps a random 16-byte id in `<data dir>/storage-id`. It is read at startup, before any store opens and before the broker registers. It is written to a temporary file, synced, renamed, and the directory synced, so a crash leaves the old id or the new one and never a mix.

The id names the data, not the node. A restart keeps it. A wipe, a replaced disk or a fresh volume at the same path leaves no file, so the next start makes a new one. A file that doesn't decode is replaced too, because a new id only claims less.

The broker sends the id to the control plane at registration, and to its peers in the replication handshake. It is a negotiated bit, `STORAGE_IDENTITY`, so a peer that doesn't offer it gets byte-identical frames to the ones it always got ([#1269](https://github.com/GetFelix/felix/pull/1269), [#1270](https://github.com/GetFelix/felix/pull/1270)).

At the start of each exchange the leader asks the connection which id the follower presented. If it differs from the one the cursor was learned under, the cursor starts over at the shard's base with nothing confirmed, and so do the follower's cursors on the group, dead-letter and counter logs. A follower that stopped cleanly and restarted presents the same id and keeps its place. If the lookup fails, the cursor is left alone and the shipping that follows meets the same failure.

That wasn't quite enough. The exchanges run concurrently, and the leader recounts the quorum mark as each one lands. Say C had confirmed past the mark and was then wiped, and B fails at once. B's answer arrives first, the recount reads C's old position, and records only the leader holds are released as acknowledged. The check had happened inside C's own exchange, which hadn't finished.

Now the mark counts a follower only once one of its requests in that pass has been answered over a connection whose id matches its cursor. Any other follower counts as holding nothing. A follower that is down counts for nothing either, though its disk may well have everything; the majority that answers carries the mark ([#1274](https://github.com/GetFelix/felix/pull/1274)).

## Who may be promoted

The leader's report now says which id each follower was counted under. The control plane holds the id each node registered with, and placement compares the two, follower by follower.

- **Equal:** the report describes the copy the follower still has. It counts while the report is believed.
- **Different:** the follower lost its directory since. It never counts from that report, however fresh.
- **Missing on either side:** a broker that predates ids. The old rule applies: it counts only while the report is fresh and was taken at the follower's current incarnation, since a restart is the only sign it may have lost its log.

The identity also fixed a second problem. Reports expire after twice the node expiry timeout plus a heartbeat, because a report says a follower was caught up and the leader kept writing. But once a leader is down, nothing refreshes its last report, and a slow control plane could let it expire and leave the shard unplaceable for good ([#1250](https://github.com/GetFelix/felix/issues/1250)). So while the report's leader is still the assignment's leader and is marked `down` or `left`, the report's age is measured to that leader's last heartbeat instead of to now.

That is safe only for a follower whose id matches. One that lost its disk would otherwise look caught up for as long as the dead leader's report was held. A follower that merely restarted keeps its id and still counts, however long ago the report was made ([#1271](https://github.com/GetFelix/felix/pull/1271)).

## When the directory survives

A wipe is the easy case: the file is gone. The harder cases keep the directory and its id but leave it holding less than peers were told. Each rotates the id for its own reason.

### A machine crash under periodic or none

Felix acknowledges a record once it has handed the bytes to the kernel with `write`. Under `periodic`, the default, and under `none`, the sync comes later. A power loss in between can drop an acknowledged tail while the directory, and so the id, survives. Under `on_commit` every record is synced first, so a crash keeps the id.

A broker records its state in `<data dir>/run-state`: a run is under way, in which fsync mode, and in which boot of the machine. It writes a clean stop only after every store has been flushed, with nothing cut short and no log stopped by a failed fsync. At the next start a relaxed run with no clean stop gets a new id ([#1294](https://github.com/GetFelix/felix/pull/1294)).

The first version rotated after any such stop, including a killed process. That was too careful. A process crash leaves the page cache with the kernel, which still writes it back, so nothing the broker acknowledged is gone. Only a machine that went down can lose it. So the record also holds the kernel's boot id, and the id is kept only if the crashed run was in the boot that is still running ([#1371](https://github.com/GetFelix/felix/pull/1371)).

Keeping it comes with three conditions:

- **The boot must be known on both sides.** An unreadable boot, another platform or a record from an older build counts as a machine crash. Silence never keeps the id.
- **The page cache is flushed first.** The broker calls `syncfs` on every filesystem under the data directory before it announces the kept id. Otherwise a later clean stop would vouch for pages only the kernel held, and a power loss after it would lose them under the same id. If the sync fails, the id rotates. This is Linux only, so elsewhere a process crash rotates and costs a re-copy.
- **A failed fsync forgets the boot.** The kernel may have dropped the pages it couldn't write, so from then on the page cache no longer vouches for what the run acknowledged.

### A directory older than the node

A volume restored from a snapshot has a valid id, and the id matches what peers know. The directory inside it is older than what they counted. Nothing in the directory shows that, under any fsync mode.

The registrations can. The broker writes the node incarnation the control plane gave it at each registration to `<data dir>/registration`. At startup a cluster member with durable storage asks the control plane for its node's current incarnation before any store opens. If the control plane is ahead of the record, the node registered at least once that this directory never saw, and the id rotates ([#1343](https://github.com/GetFelix/felix/pull/1343)).

Only a control plane that is ahead counts. One that is behind was itself restored or forgot the node, which says nothing about this directory. A control plane that can't be reached holds startup: the broker opens nothing and announces nothing until it answers, and its `/live` endpoint stays up so a probe doesn't restart it.

Some restores stay invisible. A snapshot taken during the node's current registration records the incarnation the control plane still holds, so it looks like the live directory. For those, and for a broker with no cluster, the [backup guide](https://docs.getfelix.dev/deployment/backup-and-restore/) says to delete `storage-id` before starting. `felix-broker restore-point` does it for you, before it cuts any log.

## What it costs

A rotation costs one copy started over per shard the broker follows, since its leaders compare from the shard's base. A false rotation is a spent copy. A false keep is lost data. Every rule above leans the same way.

A follower without an id, from an older build, is judged by the report's age alone. And one that restarts after its leader's last report, whose leader then dies, can't be verified, so the shard waits for the leader rather than guess.

## What we learned

A cursor is a claim about the past. Without something that refreshes it, it is a guess, and an idle system is exactly where nothing refreshes it. The fix wasn't to ask more often. It was to attach the claim to what it described.

The identity has to name the data and not the node. The node was fine, running and registered and answering. It was the thing it had counted that was gone.

Each rotation rule exists because a directory can hold less than it once did without changing: the sync that never happened, the snapshot that is older than the registration. Where the evidence is unclear, the id changes.

Finally, a check made somewhere else is not a check. The first version reset the cursor in the follower's own exchange, and the mark was counted before that exchange finished. The count has to wait for the check.
