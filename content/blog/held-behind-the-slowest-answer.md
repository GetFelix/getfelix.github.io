A failover test in Felix runs 2,100 streams on three brokers, kills one and checks that every shard keeps taking writes. In one run, a broker's replication driver stalled and the 80 shards it led stopped answering in time. That much was expected to hurt those 80 shards. What we saw was far more of them timing out.

The client sent most shards to a broker over eight shared publish streams, about 130 shards on each. The broker answered each stream in request order. So one shard waiting on a quorum held back the answers of every shard behind it on the stream, even ones that had committed long before. The broker gives a stuck publish longer than the test client's 5 s timeout, so those healthy shards timed out with it. A stall on a few shards looked to clients like the whole cluster going down.

## What we found

Felix lets a client pipeline acknowledged publishes. It writes them back to back on one stream without waiting for each answer, and the broker grants a window of how many may be unanswered at once (`FELIX_BROKER_PUBLISH_WINDOW`, 256 by default). When pipelining was added in [#819](https://github.com/GetFelix/felix/pull/819), the broker also started answering each stream's publishes in the order the stream carried them. A small structure on the broker, `AckOrder`, registers each publish as it is read and holds an answer back until every publish read before it has been answered.

That order was added for one caller, the idempotent producer, which we get to below. Every other publish paid for it too. A shard stuck on a quorum wait sat at the front, and everything behind it waited.

The client made it worse. Its stream writer, once it had nothing queued, settled every outstanding answer before it wrote again. So a stuck answer also stopped new publishes from going out on that stream.

The Rust client already worked around part of this by giving the first few shards it publishes to a stream of their own. That isolates them, but it costs throughput. On an 8 vCPU broker with a 48-shard stream and 256 B acked publishes, everything on shared streams measured about 162 MB/s, 4 dedicated streams about 125 MB/s and 16 about 97 MB/s ([#1417](https://github.com/GetFelix/felix/issues/1417)). And any shard past the first few still shared a stream with everyone else.

The waiting happened on the broker, so that is where it had to be fixed.

## Answers as they finish

The fix ([#1926](https://github.com/GetFelix/felix/pull/1926), for [#1920](https://github.com/GetFelix/felix/issues/1920)) lets a client ask the broker to answer plain publishes as they complete.

`AckOrder` now marks each registration as ordered or not. A plain acked publish, which is every acked `publish`, `publish_batch` and binary batch that isn't idempotent, is unordered. When its answer is ready, the broker writes it at once and drops its slot. An idempotent publish is ordered: its answer waits until every earlier idempotent publish on the stream has been answered. It never waits for a plain one.

Per-shard order doesn't depend on answer order. The broker commits each shard's publishes in the order it read them, so two publishes to one shard land in the order they were sent whichever answer arrives first. A client matches each answer to its request by `request_id`, which the Rust client already did.

The client side changed too. When the broker grants the new behaviour, the writer with answers outstanding and nothing queued waits for whichever comes first, an answer or a new request. It keeps writing while a stalled answer is out and settles each answer as it arrives. The awkward part is that reading an answer is not cancel-safe: dropping a half-finished read would lose bytes off the stream. So the read in progress takes ownership of the receive stream and its buffer and stays pinned across loop iterations, and hands them back when it finishes. The writer is still one task, with no extra reader task or channel in the path.

## Why idempotent publishes keep their order

An idempotent producer numbers its batches with consecutive sequences. The leader checks each sequence against the last one it appended for that producer. If batch n fails before it is appended, batch n+1 arrives with a sequence the leader didn't expect and is refused with `sequence_gap`.

The producer's recovery rule depends on which failure it sees first. It keeps up to 64 batches in flight, since the leader remembers 64 sequences per producer. When one fails, it treats that batch and everything behind it as in doubt and re-sends them, in order, under the same sequences. The leader answers the ones it already holds from memory and appends the rest.

That only works if the first failure the producer reads is the earliest one. With answers in request order, n's failure always comes before n+1's `sequence_gap`. With answers in completion order, the gap could arrive first, and a producer reading answers off the wire would take a consequence for the cause and start its re-send at n+1, which the leader can only refuse again. So idempotent answers stay in request order among themselves, whatever else shares the stream.

## Old clients see the same bytes

Felix adds wire features without bumping a version. A client offers features in its `auth`, the broker answers with the ones it agrees to, and each side only changes behaviour for features both named. A frame flag selects how a payload is laid out, so an unknown flag is rejected. This change alters no payload, only the timing and order of answers, so it is a feature bit instead: `FEATURE_PUBLISH_ANSWER_ON_COMPLETION`, `0x40` in the extended feature word.

A client offers it alongside the pipelining bit. The broker answers it back only when it grants that client a publish window and the client offered it. Everything else falls out of that rule.

An older client never offers the bit, so the broker never sets it and keeps request order for that client's every publish. Its `auth_ok` carries no new bit, and every frame after it is byte for byte what it was. A newer client talking to an older broker hears nothing back about the bit, so its writer keeps its old behaviour and expects request order. A peer from before negotiation gets a plain `ok`, and the only safe reading of that silence is the original flag set, which is frozen.

## What it costs

The window is unchanged. A publish stuck on a quorum still holds its slot until it is answered, so enough stuck publishes on one stream can still fill its window and stop the broker reading that stream. That keeps per-stream backpressure as it was. It also means a lost answer matters more than it looks. Before, a broker that lost an answer noticed because later answers were held behind it, and closed the stream once the oldest held answer was overdue by twice the enqueue and ack waits. A lost plain answer now holds nothing back, but it keeps its window slot for good. So on a stream that answers on completion, the broker watches the oldest unanswered publish of any kind, and closes the stream when that one is overdue. The client then sees every unanswered publish on it fail with `AckLost`.

Idempotent publishes that share a stream still wait for each other, including ones from different producers.

On the client, the writer pays one extra `select!` poll of its request queue, and only when the broker granted the bit.

## What we learned

An ordering promise has a price, and whoever doesn't need it pays it too. Request order was right for the idempotent producer and wrong for everyone else on the stream. The fix keeps the promise for the caller that relies on it and drops it for the rest.

The other lesson is to fix the wait where it happens. Splitting shards onto their own streams limited the damage, but the answers were held on the broker, and only the broker could let them go.
