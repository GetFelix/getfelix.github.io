A client writes record 1 to a shard with three replicas and gets an acknowledgement. Two failovers later the shard has a new leader, and that leader never held record 1. It opens anyway, and serves the shard as if record 1 had never been written.

Nobody lost a disk and no clock lied. Placement replaced two leaders one after the other, and each time placement promoted a follower that the last leader had reported as caught up. Both reports were taken before the followers they named had answered anything.

The TLA+ model of a Felix shard found this run ([#1922](https://github.com/GetFelix/felix/issues/1922)). The code followed the same rule as the model, and [#1924](https://github.com/GetFelix/felix/pull/1924) fixes it by putting a floor under the leader's report.

## A few terms first

A **shard** is one slice of a stream. Its **replica set** is the brokers that keep a copy, here three of them. One is the **leader**: it takes writes and ships them to the others, the **followers**. Each time a new leader takes over, the shard's **generation** goes up by one.

On a `Quorum` stream with the `majority_ack` cluster feature finalized, the leader **acknowledges** a write once a majority of the replica set, itself included, has answered that it holds the write at the leader's generation. With three replicas, that is two.

The leader also sends the control plane a **report**: which followers are caught up, and how far each has got. When a leader is lost, **placement** in the control plane promotes a follower, and only one that the leader's last report named as caught up.

Before a promoted leader serves, it **fences**. It asks a majority of its replica set to stop taking writes from older leaders and to say what they hold, then takes the furthest log it hears about. With `joint_fence`, it also needs a majority of the set from the generation before.

## What we found

Four brokers, a, b, c and d, and a replica set of three. Figure 2 follows the run the model found.

a leads first, with nothing written yet. Placement gives up on it, and b is promoted at generation 2 with the set {b, c, d}. c answers b's fence, b and c are a majority of both {b, c, d} and the old {a, b, c}, and b opens.

A client writes record 1. b ships it to d, d answers, and b acknowledges: b and d are two of three. c has not got it yet.

b's last report names c and d as caught up. Under `majority_ack` a follower was named caught up when it held what a majority held at the leader's own generation. Before any follower has answered at generation 2, that offset is 0, and every follower is at or past 0.

Placement gives up on b and promotes d, which the report named, at generation 3 with the set {a, c, d}. d fences {a, c, d} and {b, c, d}, c answers, and d opens. d holds record 1, so nothing is lost yet.

Before d has shipped anything, it sends its own report. Nobody has answered at generation 3, so it names a and c as caught up at offset 0.

Placement gives up on d too, and promotes a, whose log is empty, at generation 4 with the set {a, b, c}. a fences {a, b, c} and {a, c, d}. c answers, and a and c are a majority of both sets. Neither of them holds record 1. The furthest log a hears about is empty, and a opens without the record.

b and d still hold record 1, but they are out of reach, and a needed neither of them for its fence.

In the model, each failover also swaps a member out for a spare. Felix's placement keeps the set of a fenced shard on failover, and the set changes instead when a replacement is seated for a drained follower or a broker is restored. The run needs only that the set changes between the acknowledgement and the promotion that loses it. The path that changes it does not matter.

## Why the rule looked safe

Felix already floored the report at the log a new leader inherited, for shards whose leader acknowledges a write only once its report about it has reached the control plane. That floor came from an earlier issue with the same shape: a follower named before it answered, then promoted without a record. A shard acknowledging by its followers skipped it. The comment above the exemption in `driver/shard.rs` gave the reason: "the promoted leader fences a majority and takes the furthest log instead."

That holds while the set stays the same. Any two majorities of {b, c, d} share a broker, so whatever majority the next leader fences includes someone from {b, d}, and the record comes back. Once the set changes, the majorities are drawn from different sets. {a, c} is a majority of {a, c, d} and of {a, b, c}, and it shares nobody with {b, d}.

## How the model found it

`docs/formal/FelixShard.tla` models one shard: leases, replication to a majority, reports, promotion and fencing. Among its invariants, the properties TLC checks in every reachable state, is `AckedHeldByLeader`: every leader that has opened holds every record acknowledged at its generation or below. TLC is the TLA+ model checker. It explores every interleaving the spec allows, up to the limits a config sets, and prints a trace when an invariant fails.

The model has a switch for the floor. `Inherited(b)` counts the records in b's log written before b's own generation, which bounds anything an earlier leader acknowledged. `ReportAt(b)`, what a follower must hold to be named, takes the maximum of the majority mark and, with `ReportFloor`, `Inherited(b)`. With `ReportFloor = FALSE` it falls back to the mark alone, which is what the code did under `majority_ack`.

The config that failed, `FelixShardReplacedPendingLeftTwiceAllLogReport.cfg`, combined the pieces that make the run possible: four brokers with d as a spare, acknowledgement by followers (`AckByFollowers = TRUE`), joint fencing, two failovers, and `Promotion = "leader-report"`, which promotes only a replica the leader's last report lists as caught up, as placement does. It was expected to pass. TLC reported a violation of `AckedHeldByLeader` and a 22-state trace, and the issue went up marked as a possible bug, unconfirmed against the code.

Confirming it meant mapping each step of the trace to code on main. The report bound was `if by_followers || stepped_down() { promised }`. Placement's `is_caught_up` and `promote` accepted any member named caught up. Each fence answer matched what the fence code does. Every step had a line of code behind it, so the trace was a real bug and not a quirk of the model.

## The fix

The floor now applies in both modes, with or without `majority_ack`. Only a leader that already knows it has been deposed skips it, as before, because it counts nothing more:

```rust
if stepped_down() {
    promised
} else {
    promised.max(inherited.min(tail))
}
```

In the run above, d inherited record 1 at generation 3, so its floor is offset 1. a and c are named only once d has shipped record 1 to them and they have answered. If placement gives up on d before that, there is nobody to promote but a broker that holds the log, and the shard waits for one.

A cache shard has a second log for counter updates, and its report had the same exemption. The counter floor now applies by followers too, and counts from the start of the leader's current stint, as the shard's own log does.

Nothing changes in what a client is told. The floor only decides who the report names. The acknowledgement still comes from the majority mark.

With the floor on, the model's twin config with `ReportFloor = TRUE` describes the code. A bounded local run of it went deeper than the point where the unfloored config fails, with no violation.

## Two more fixes the floor exposed

A stricter floor names fewer followers, and that made a cluster test, `seating_a_replacement_keeps_what_the_old_set_acknowledged`, wait forever. Four brokers, three replicas. The leader acknowledges records on itself and a follower, `departing`, while the other follower, `lagging`, is cut off. Then `departing` is drained and the fourth broker joins in its place, also cut off from the leader, and the leader dies.

The only copy holding the leader's log was on the draining broker, and placement never promoted a draining broker. Before the fix, the test passed because the leader had named `lagging` at offset 0 and placement promoted it. That happened to be safe there, because the drained copy was still in the set `lagging` fenced. With the floor, nobody was named, and the shard had no leader. Placement now promotes a caught-up follower on a draining broker when the leader is gone and no live follower is caught up. The drain moves the shard off it afterwards, as it would anyway.

The test still did not pass. The new leader on the draining broker needed `lagging`'s fence answer for a majority, and that answer never counted.

Each broker's data directory carries a storage identity, a random id that changes when the directory may hold less than its peers were told ([The follower that forgot](/blog/the-follower-that-forgot.html) covers it). A report names the id each follower was counted under. The next failover's fence names each member by that id and counts an answer only from that copy.

Seating the joiner changed the set but kept the leader. The leader started the new generation with fresh cursors, and a follower's id is learned only when it answers. `lagging` was cut off, so the report named it with an empty id, and no answer from `lagging` could ever match that. Before the floor this did no harm in the test, because placement promoted `lagging` itself.

The fix carries names across a set change. When the leader moves to a new generation without a promotion, it keeps the id it knew each follower by, the copy the follower last answered from or else the one it inherited. A promotion that names the copies itself still replaces them. The model already worked this way: `FelixShard.tla` resets those names only at a promotion.

## What it costs

The floor costs availability right after a failover. No follower is named until it has copied everything the new leader inherited. If the new leader is lost before that, the shard waits for a broker that holds the log instead of promoting one that might not. The draining fallback keeps a drain under way from turning that wait into an outage.

On the hot path the change costs nothing we could measure. An A/B run with three replicas compared steady throughput, a burst through a promotion, and time to the first acknowledgement after killing the leader. The ratios for throughput and median latency came out between 0.98 and 1.01, inside the run-to-run noise.

## What we learned

"The next leader fences a majority" is a safe argument only when the majority comes from the set that acknowledged the write. Any argument that relies on majorities overlapping has to say which sets they are drawn from, because sets change.

The model and the code had the same exemption, and the model had the switch to turn it off. It took a config that combined follower acknowledgement, promotion by report and a changing set before TLC could reach the trace. It found it there because nothing in the spec forbade the combination.

A stricter safety rule makes liveness problems show up. Both follow-up bugs were hidden by a follower named at offset 0 that happened to be safe to promote. The empty name was there before the floor. The floor just stopped anything from working around it.
