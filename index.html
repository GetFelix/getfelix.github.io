Why Felix

Infrastructure should make software simpler.

Most applications piece together one system for events, another for queues, another for state, and one more to move data between them. In Felix, events, work and state are three ways of operating over the same data.

One system. One durable foundation.
Multiple ways to use your data.

Fast enough for real-time applications, durable enough to trust, and simple enough that you can easily figure out what happened when something fails.

How Felix is different

One log where you'd run four systems

Streams, key-value caches, queues and counters all sit on one replicated log, behind one access model. And a slow subscriber falls behind on its own.

Features

What Felix does

One replicated log behind streams, caches and queues

A stream reads the log forward, a cache keeps the latest value for each key, and a queue is a cursor a consumer group shares. All three use the same durability, recovery and replication.

Resume from an offset

Records on a durable stream carry their log offsets. A subscriber resumes after the last one it saw, and a jump between offsets shows exactly which records it missed.

Slow subscribers stay separate

Each subscriber has its own bounded queue. A publisher never waits for a slow subscriber, and the others keep their pace.

Quorum streams

A Quorum stream acknowledges a publish once a majority of its replicas hold it durably. With no majority reachable, it is never acknowledged: the publish times out and reports its outcome as unknown.

Clients for Rust, Python and TypeScript

All three speak QUIC through one shared implementation and pass the same conformance suite. felixctl covers the command line.

felix-clientRustPythonTypeScriptfelixctl

Conditional publish

A publish can name the offset it expects to start at. When two writers race for one offset, exactly one succeeds, and the refused one writes nothing.

Range reads and record times

Read a bounded slice of a durable stream without subscribing. Each durable record keeps its append time, and a client can find the first record at or after a time.

Fine-grained access

Grants go down to one cache key or key prefix, and exchanged tokens can be narrowed by action and resource. One Rust client can act for many users, each request checked against its own token and each user held to their own limits. A gateway can trade a user's token for a delegated one that names it as the actor.

Failover that keeps acknowledged writes

A lost leader is replaced only by a replica that holds its log, and the new leader fences a majority of the replicas before it serves. Followers report a leader that stops answering, so a durable Quorum stream can fail over in about five seconds.

Kafka clients

Kafka producers, and consumers that assign their own partitions, work against durable streams: each stream is a topic and each shard a partition. Kafka consumer groups and transactions are not supported.

Look inside a cluster

felixctl inspect asks each broker what it holds: a shard's leader, lease and follower lag, or every subscription with its queue depth and drops. felix-broker inspect segments checks a data directory offline and says what startup would do with it.

Quickstart

Publish and subscribe

Once felixctl has a context for your cluster, each step is one command. The guide starts a local cluster with a stream named orders and a cache named users.

Try it with felixctl 
# one terminal
felixctl sub orders

# another
felixctl pub orders 'hello'
felixctl cache put users alice 'online'
felixctl cache get users alice
felixctl topology orders
use felix_client::{AckMode, Client, ClientConfig};
use std::net::SocketAddr;

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let quinn = quinn::ClientConfig::with_platform_verifier();
    let config = ClientConfig::optimized_defaults(quinn);
    let addr: SocketAddr = "127.0.0.1:5000".parse()?;
    let client = Client::connect(addr, "localhost", config).await?;

    let publisher = client.publisher().await?;
    publisher
        .publish("acme", "prod", "events", b"Hello Felix".to_vec(), AckMode::None)
        .await?;

    let mut subscription = client.subscribe("acme", "prod", "events").await?;
    while let Some(event) = subscription.next_event().await? {
        println!("Received: {:?}", event.payload);
    }
    Ok(())
}
import os
import felix

with felix.Client(
    "127.0.0.1:5000", tenant_id="acme", token=os.environ["FELIX_TOKEN"]
) as client:
    with client.subscribe("acme", "prod", "events") as events:
        client.publish("acme", "prod", "events", b"Hello Felix")
        for event in events:
            print("Received:", event.payload)
import { Client } from "felix-client";

const client = await Client.connect("127.0.0.1:5000", "acme", process.env.FELIX_TOKEN!);
const events = await client.subscribe("acme", "prod", "events");
await client.publish("acme", "prod", "events", Buffer.from("Hello Felix"));

for (;;) {
  const event = await events.nextEvent();
  if (event === null) break;
  console.log("Received:", event.payload.toString());
}
Performance

Measured on one broker

Preview results from Felix 0.6.0 on one 8 vCPU Azure VM with local NVMe, driven by four load generators in the same region. "Durable" means the broker fsyncs before it acks. These are single-broker numbers, and replicated multi-node results are coming.

0.6.0-preview · single region · more results coming

4.1GB/s

Published, in memory

4 KiB records in batches of 64, fire-and-forget. The broker was CPU-bound at 7.4 of 8 cores. Mean of 3 runs.

1.43GB/s

Published, durable

Same workload with an fsync before each ack. 97% of what fio measured on the same NVMe array. Mean of 3 runs.

2.27M records/s

Acked, durable, small records

256 B records in batches of 64, fsync before each ack. 2.27 to 2.29 million across 3 runs.

345µs p50

Durable publish to delivery

One 256 B publish in flight, received by a subscriber on a second connection after the fsync. p99 445 µs. 2 runs.

Performance analysis is ongoing. A full write-up with the method and every run is coming.
