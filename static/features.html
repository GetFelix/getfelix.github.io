Streams, state and work on one log

One replicated log behind streams, caches and queues

A stream reads the log forward, a cache keeps the latest value for each key, and a queue is a cursor a consumer group shares. All three use the same durability, recovery and replication.

Resume from an offset

Records on a durable stream carry their log offsets. A subscriber resumes after the last one it saw, and a jump between offsets shows exactly which records it missed.

Slow subscribers stay separate

Each subscriber has its own queue, bounded by count and by bytes (256 MiB by default). Under the default policy a publisher never waits for a slow subscriber, and the others keep their pace.

Quorum streams

A Quorum stream acknowledges a publish once a majority of its replicas, the leader counted, have written it to their logs. With no majority reachable, it is never acknowledged: the publish times out and reports its outcome as unknown.

Failover that keeps acknowledged writes

A lost leader is replaced only by a replica that holds its log, and the new leader fences a majority of the replicas before it serves. Followers report a leader that stops answering, so a durable Quorum stream fails over in about five seconds. A new cluster turns this on when its first broker registers; an upgraded one, once an operator finalizes its fleet features.

Conditional publish

A publish can name the offset it expects to start at. When two writers race for one offset, exactly one succeeds, and the refused one writes nothing.

Range reads and record times

Read a bounded slice of a durable stream without subscribing. Each durable record keeps its append time, and a client can find the first record at or after a time.

Look inside a cluster

felixctl inspect asks each broker what it holds: a shard's leader, lease and follower lag, or every subscription with its queue depth and drops. felix-broker inspect segments checks a data directory offline and says what startup would do with it.

Fine-grained access

Grants go down to one cache key or key prefix, and exchanged tokens can be narrowed by action and resource. A client can act for many users over shared connections, on one broker or across a cluster, each request checked against its own token. A gateway can trade a user's token for a delegated one that names it as the actor, or for one with no permissions that only authenticates its connections.

Revocation reaches open streams

Revoking a principal, or removing a rule that reached it, ends its open streams, subscriptions, cache watches and Kafka connections on every broker within about one control-plane sync, with a revoked error. Deleting a stream ends its subscriptions with stream_deleted.

Sharding

The key picks the shard

A stream can be split into shards, and each shard is its own ordered log. A record's routing key is hashed to pick its shard. The same key always picks the same shard, on every broker and in every client, so records with one key stay in order.

Shards spread a busy stream over brokers. Each shard has a leader that takes its writes and replicas on other brokers. A record without a key goes to shard 0.

Streams in the docs

Why jump hash

A stream maps a key's hash to a shard either with jump consistent hashing or with the hash modulo the shard count. If a stream grew from 4 shards to 5, jump hash would move only the keys bound for the new shard, about 1 in 5 (1,941 of 10,000 sample keys). Modulo would move most of them (7,993 of 10,000).

A stream's shard count can't change yet. The mapping is fixed when the stream is created, so choosing jump hash then is what keeps growing it cheap later. New streams get jump hash once an operator finalizes the jump_hash_routing fleet feature. Older streams keep modulo, so no live key moves.

Kafka compatibility

Kafka clients

Kafka producers, and consumers that assign their own partitions, work against durable streams: each stream is a topic and each shard a partition. Kafka consumer groups and transactions are not supported.

  • Producers
  • Consumers that assign partitions
  • Consumer groups (not supported)
  • Transactions (not supported)

Without groups or transactions, Kafka Connect, Kafka Streams and ksqlDB don't run.
